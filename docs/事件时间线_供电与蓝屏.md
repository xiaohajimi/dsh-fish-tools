## 二、关键发现（对"13 倍"的归因很重要）

### ⓿ 操作者补充（2026-11-20 01:40）：17:43 那次是「切核显 + 装新 CPU 驱动」

**这让变量从三个变成四个**：

| # | 变量 | 时间 | 能不能复现 |
|---|---|---|---|
| 1 | 删 Ryzen Controller 33 W 锁 | 17:2x | 可以（不建议） |
| 2 | 最大处理器状态 95% → 100% | 17:2x | 可以，安全 |
| 3 | 修插排 / 供电恢复 | 20:00 后 | 不能 |
| 4 | **切换核显 + 安装新 CPU 驱动** | **17:43** | 理论可以，但风险大 |

**"13 倍"现在是四个变量叠加的结果，归因彻底不成立。**
唯一还能干净做的是 #2（处理器状态 95 vs 100）。

### ① Windows 里**没有任何 CPU 限速事件**

```
查了 Kernel-Processor-Power 的 ID 37/38（处理器被限速的报告）
→ 30 小时内一条都没有
只有 ID 55（电源管理能力报告，纯信息性）
```

**推论**：Ryzen Controller 的 33 W 限制是**直接写 EC/固件级 PPT/TDC/EDC**，
操作系统完全看不到，所以事件日志里没有任何痕迹。
这和"删掉软件后 CPU 基准从 21.74 秒回到 1.67 秒"是吻合的——
**限制在 OS 之下，只有实测才能发现。**

### ② "意外关闭"只有两次，都在高强度训练时

```
15:42:22（训练 100/252 步时）
20:35:29（训练另一轮时）
两次都是 Kernel-Power 41 + EventLog 6008
```

而 17:43、17:47、20:39、22:19 的重启全是**人为/程序发起**（User32 1074），不是故障。

### ③ 物理供电因素目前只有间接证据

```
已知：用户睡眠时碰松插排 → 零线偏移 → 供电异常
当时观测：CPU ~500 MHz、ChargeRate = 0（接电源但不充电）
```

但这段时间没有留连续采样，**无法证明"限频是插排导致还是 33 W 导致"**。
因此先前那份"13 倍"的归因，只能写成：

> 三个因素叠加（33 W 软件锁 + 处理器状态 95% + 供电异常），
> **无法单独归因**。要分开验证，需要分别、单独地复现。

## 三、可以干净复现的部分（唯一）

**最大处理器状态 95% → 100%**

```
方法：powercfg 改 PROCTHROTTLEMAX，配对交替测（95/100/95/100）
条件：同一天、同一分钟区间、背景负载一致
指标：CPU 单线程基准耗时（2000 万次循环）
```

**其他两项不可复现**：
- Ryzen Controller 33 W：软件已卸载，重装复现可以但不值得（会真的把机器锁慢）
- 插排零线偏移：物理事故，**绝不故意制造**

> "我当时以为是驱动问题，后来发现是 CPU 被第三方软件锁在 33 W。

> **所以那 13 倍不能单独归功于解决锁频。** 能单独验证的只有第三项，
